# C parity check, 2026-10-14

Check of the Go port (package `netcode`) against the C reference
(mas-bandwidth/netcode), which is normative. STANDARD.md in this repository is
a verbatim vendored copy of the C repo's spec and is the primary source for
what C mandates; behaviour that STANDARD.md does not cover is compared against
the C source when a checkout is named. This run had no C checkout reachable
(`NETCODE_C_DIR` unset, no `netcode.c` on the machine), so those items are
marked QUESTION with what a checkout would settle.

Checked commit: `7d4daec` (sprint/netcode-go-port base).

Verdicts: MATCH (compared against STANDARD.md and/or the committed golden
vectors), DIVERGENCE (an intentional or memory-safety-only difference, with a
reason), BUG (the port disagrees with C where C is right), QUESTION (needs the
C source to settle).

---

## 1. Wire format

MATCH. Compared against STANDARD.md "Packets" and the committed C-generated
golden vectors in `testdata/packet_*.bin` (exercised by `wire_compat_test.go`).

- Seven packet types 0..6: `packet.go:4-13`, matching STANDARD.md.
- Prefix byte = low four bits packet type, high four bits count of sequence
  bytes: `packet.go:112` (`p.packetType() | uint8(sequenceBytes)<<4`); read back
  at `packet.go:280` (`prefixByte & 0xF`) and `packet.go:292`
  (`prefixByte >> 4`).
- 1-8 variable-length sequence bytes, reversed (LE, high zero bytes omitted):
  `packet.go:63-73` (`sequenceNumberBytesRequired`), `packet.go:118-122`.
- Nonce = four zero bytes then the sequence as 64-bit little endian:
  `crypto.go:91-97` (`packetNonce`).
- AEAD associated data = version info + protocol id + prefix byte:
  `packet.go:78-85` (`packetAdditionalData`).
- Packet sizes: request 1078 bytes (`packet.go:205`,
  `1+13+8+8+24+1024`), response 8 + 300 = 308 (`packet.go:367`,
  `8+challengeTokenBytes`).
- Address type values 1 (IPv4) and 2 (IPv6): `address.go:10-14`,
  `token.go:38-53` (`writeAddress`), `token.go:55-70` (`readAddress`).

## 4. Server

MATCH (with two notes below). Compared against STANDARD.md "Server-Side
Connection Process" and "Nonce Reuse and Server Restarts".

- Global sequence seeded at create AND at start: `server.go:208` (create,
  `1 << 63`) and `server.go:267` (Start, `1 << 63`). The comment at
  `server.go:262-266` documents the reseed requirement.
- Restart floor and ordering: the `connectTokenExpireTimestamp <
  minConnectTokenExpireTimestamp` check runs in `packet.go:238-241`
  immediately after the expiry check and before the decrypt, matching
  STANDARD.md "Processing Connection Requests" order.
- Challenge and denied handling: `server.go:521-525` (denied when full),
  `server.go:543-561` (challenge send + `challengeSequence++`).
- Response accepted only with the mapping's own challenge: the response is
  decrypted with the global `challengeKey` and the encryption mapping for the
  source address (`server.go:612-652`). C uses the same global challenge key
  scheme, so no per-client challenge sequence is stored on either side.
- Client timeouts: `server.go:833-860` (`checkForTimeouts`), timeout from the
  token's `timeout_seconds`.
- Keep-alive rate 10 Hz: `netcode.go:79` (`packetSendRate = 10.0`),
  `server.go:822`.
- Redundant disconnect packets (10): `netcode.go:80`
  (`numDisconnectPackets = 10`), `server.go:367`.
- Max clients 256: `netcode.go:58` (`MaxClients = 256`).
- Loopback clients: `server.go:1033-1067`.

Note A (DIVERGENCE, seam only, no wire effect): `time.Now().Unix()` is read
inside the request path at `server.go:502`, `server.go:704` and `server.go:770`
(and `client.go:330`) for the connect-token expiry timestamp, where C passes a
single `current_timestamp` per update. This means the differential test and
unit tests at the `readPacket` level must pass explicit timestamps (they do:
`readAndProcessPacket`/`ProcessPacket` accept `currentTimestamp`), and
`Server.Start` seeds `minConnectTokenExpireTimestamp` from the wall clock
(`server.go:270`) instead of the time argument. The token-expiry check reads
wall-clock seconds while the protocol clock is an argument, which can disagree
in a test that fast-forwards time. A card would thread one timestamp through.

Note B (DIVERGENCE, benign): `Stop()` sets `globalSequence = 1 << 63`
(`server.go:442`) where C sets it to 0; both are reseeded to `1 << 63` in
`Start()` (`server.go:267`), so this is not observable.

## 6. Receive loops and callbacks

FINDINGS (C 1.4.6 to 1.4.8 behaviour; not all of it is in STANDARD.md, and the
C source was not reachable this run, so C file:lines below are from the audit
card and unverified — each is a BUG or DIVERGENCE candidate for a follow-up
card).

- Empty datagrams skipped and every drain capped: MATCH. Empty/overshort
  datagrams dropped at `server.go:724` (`len(packetData) <= 1`) and
  `socket.go:144` (`bytes <= 0`); drains are capped by `serverMaxReceivePackets`
  (`server.go:70,807`) and `clientMaxReceivePackets` (`client.go:403,395`).

- Payload packet carries eight bytes of readable slack behind the payload:
  DIVERGENCE (allowed). C's `netcode_write_packet` requires the caller to leave
  8 bytes of slack after a payload packet for its decrypt-in-place; the port
  writes to Go slices and allocates the payload at `packet.go:395`
  (`make([]byte, decryptedBytes)`), so no slack contract is needed and none is
  enforced. Go is memory-safe; this is not wire-observable.

- A config with `override_send_and_receive` set and a missing override is
  refused at create (C error codes 7 and 8): BUG. The port accepts such a
  config and silently drops the outbound packet:
  `serverCreateSocket` (`server.go:111-136`) returns `nil, nil` whenever
  `OverrideSendAndReceive` is set, never checking that `SendPacketOverride` or
  `ReceivePacketOverride` is non-nil; `sendGlobalPacket` then sets
  `sendPacketOverride` to the nil callback (`server.go:289-292`) and
  `sendPacketToAddress` (`socket.go:187-203`) silently skips the send. Same on
  the client: `clientCreateSocket` (`client.go:71-88`) and
  `sendPacketToServerInternal` (`client.go:415-418`). C returns create error
  codes 7 and 8 here (C `netcode.c`, create path — line to be confirmed against
  a checkout). A card would refuse at `NewServerDual`/`NewClientDual` when
  `OverrideSendAndReceive` is set with a nil override.

- Loopback connect is refused when the loopback callback is unset: BUG.
  `ConnectLoopbackClient` (`server.go:1033`, send at `server.go:965`) and
  `ConnectLoopback` (`client.go:642`, send at `client.go:579`) do not refuse a
  nil `SendLoopbackPacketCallback`; the send path then calls a nil callback
  (`server.go:965`, `client.go:579`), which panics. C refuses (C
  `netcode.c:5398-5404` and `3654-3660`, unverified). A card would add the nil
  callback guard and return an error.

- Address-to-string buffer contract (`NETCODE_MAX_ADDRESS_STRING_LENGTH`):
  DIVERGENCE (allowed). The port keeps the constant (`netcode.go:69`,
  `maxAddressStringLength = 256`, used to cap input in `address.go:90-92`) but
  formats into Go's dynamically-sized strings (`address.go:165-181`) rather than
  a fixed `char` buffer, so there is no truncation contract to violate. Not
  wire-observable.

- A failing simulator allocation drops the packet and keeps the queued entry:
  QUESTION. The port's simulator copies the packet with
  `append([]byte(nil), packetData...)` at `simulator.go:81`; on allocation
  failure Go panics rather than C's drop-and-keep-the-entry behaviour, and the
  entry is not separately marked queued. Confirming the exact C behaviour needs
  the C simulator source (`netcode.c` simulator `SendPacket`).

## 7. Randomness

MATCH. The port draws keys and nonces from `crypto/rand` via `RandomBytes`
(`crypto.go:33-37`), used for connect-token keys/nonces (`token.go:32-33`,
`token.go:333`) and the server challenge key (`server.go:269`). A stubbed RNG
cannot silently return uninitialised memory: `rand.Read` failure panics
(`crypto.go:34-36`), so the port fails loudly rather than silently using
garbage, which satisfies IMPLEMENTERS.md section 4's intent.

## 8. Constants and defaults, declared version

FINDING. The port declares `VersionFull = "1.4.8"` (and 1/4/8 major/minor/patch)
at `netcode.go:45-48`, which tracks the C reference's 1.4.8 (this repo's base
commit `7d4daec` is titled "enforce C 1.4.8 lifecycle"). `CLAUDE.md` DECISIONS
#2 (`CLAUDE.md:10-12`) still says `VersionFull` "1.4.0"; that prose is stale
and is the only place claiming 1.4.0. Whether 1.4.8 is exactly current
`NETCODE_VERSION_*` in C is a QUESTION that needs a C checkout to confirm, but
the code and the base commit agree on 1.4.8, and `versionInfo` (`NETCODE 1.02`)
never moves (`netcode.go:76`). A card would fix the stale CLAUDE.md sentence.

## 9. Interop pin / golden vectors

FINDING. The golden vectors are `testdata/*.bin` with their generator
`testdata/generate_vectors.c`, asserted byte-for-byte by
`wire_compat_test.go`; live interop is `c_interop_test.go`. The vectors are
committed but are not pinned to a specific C commit in this repository: CI
regenerates them from C `main` unpinned (`CLAUDE.md:25`), so the effective pin
is "C main at CI time". Whether that is the current C reference at audit time
is a QUESTION needing a C checkout (and the C `main` HEAD) to settle. A card
would record the exact C commit the committed `.bin` files were generated from
(or pin CI to one).
